# ADR: Выбор стека мониторинга, централизованного логирования и оповещения для целевой архитектуры TradeWare

## 1. Статус
Рассмотрение к реализации пилотного прототипа / POC

## 2. Контекст и проблематика
Внедрение асинхронного сервиса на базе Spring Batch решило проблему производительности СУБД PostgreSQL и разгрузило монолит WildFly. Однако разделение системы на несколько компонентов (Angular-фронтенд, монолит WildFly, очередь сообщений, Spring Batch сервис) породило проблему распределённости.

### Текущие вызовы (As Is для наблюдаемости):
* **«Слепая зона» при авариях:** Логи распределены по разным контейнерам. Если отчет на 1 млн строк падает в середине обработки, инженерам приходится вручную заходить в каждый контейнер, чтобы сопоставить логи очереди, WildFly и Spring Batch.
* **Нагрузка от системных таблиц:** Системные таблицы метаданных Spring Batch (`BATCH_STEP_EXECUTION` и др.) содержат числовую информацию о чанках и статусах, но регулярные SQL-запросы к ним со стороны Grafana или аналитиков создают паразитную нагрузку на основную транзакционную базу данных PostgreSQL.
* **Отсутствие проактивности:** О сбоях в пиковый строительный сезон (весна-лето) поддержка узнает от клиентов, так как в инфраструктуре нет автоматических триггеров и каналов оперативного оповещения инженеров.

## 3. Критерии выбора решения
* **Разделение обязанностей (Separation of Concerns):** Инструменты мониторинга не должны использовать ресурсы основной бизнес-БД PostgreSQL.
* **Полнотекстовый поиск по Stack Trace:** Возможность мгновенного поиска по сложным Java-исключениям, характерным для экосистемы TradeWare.
* **Сквозная трассировка:** Наличие механизмов корреляции логов из разных сервисов по уникальному идентификатору сессии (`trace_id`).
* **Интеграция с Java/Spring:** Нативная поддержка метрик Micrometer и формата логирования Logback.

## 4. Принятое решение: Раздельный стек Prometheus + Grafana (Метрики) и ELK (Логи)

Для обеспечения полной наблюдаемости принято решение внедрить гибридный стек, где сбор числовых метрик отделен от сбора текстовых логов.

### 4.1. Сбор и визуализация числовых метрик: Prometheus + Grafana
* **Что делаем:** Сервис Spring Batch и монолит WildFly через встроенные библиотеки (Spring Boot Actuator / Micrometer) открывают HTTP-эндпоинт `/actuator/prometheus`. Сервер **Prometheus** раз в 15 секунд самостоятельно забирает (Pull-модель) числовые метрики производительности и бизнес-показатели. **Grafana** подключается к Prometheus и строит дашборды.
* **Зачем это нужно:** Это позволяет в реальном времени отслеживать выполнение SLA (время обработки 2 000 строк < 30 секунд), утилизацию памяти JVM контейнеров и количество активных коннектов к БД вообще не нагружая PostgreSQL аналитическими запросами.
* **Оповещение (Alerting):** В Grafana настраиваются триггеры. Если статус джобы в Prometheus меняется на `FAILED` или время обработки чанка растет, Grafana мгновенно отправляет экстренное сообщение дежурному инженеру через **Telegram Bot / Slack Webhook**.

### 4.2. Централизованное логирование: Стек ELK (Filebeat + Logstash + Elasticsearch + Kibana)
* **Что делаем:** Приложения переводятся на вывод логов в формате **JSON** напрямую в стандартный поток `stdout`. Легковесный агент **Filebeat** на каждой ноде облака GCP мгновенно перехватывает эти потоки и пересылает в **Logstash**. Logstash парсит поля и отправляет структурированные документы в **Elasticsearch**. Разработчики и поддержка используют **Kibana** для анализа.
* **Зачем это нужно:** Каждая строка лога размечается сквозным `trace_id` (Correlation ID), который генерируется на Angular-фронтенде и пробрасывается через WildFly и очередь в Spring Batch. Поиск в Kibana по этому ID выводит на экран весь путь отчета от момента загрузки файла пользователем до падения конкретной строки в чанке. Полнотекстовый индекс Elasticsearch позволяет группировать Java Stack Traces по типам ошибок.

## 5. Альтернативные варианты, которые рассматривались

### Вариант 1: Использование только системных таблиц метаданных Spring Batch
* *Почему отклонен:* Эти таблицы созданы для контроля транзакций и перезапуска джоб с точки останова (State Management). Попытка строить на них живой мониторинг через SQL-запросы приведет к блокировкам в PostgreSQL. Кроме того, они не содержат логи фронтенда, WildFly и брокера сообщений — цепочка трассировки ломается. 

### Вариант 2: Стек PLG (Prometheus + Grafana Loki + Promtail/Fluentbit)
* *Почему отклонен:* Grafana Loki ориентирован на дешевое хранение логов без полнотекстового индексирования (индексируются только метаданные/теги). Для микросервисов на Go/Node.js это отлично подходит. Но в экосистеме TradeWare (Java 11, WildFly) ошибки сопровождаются огромными Stack Traces. Поиск по тексту ошибки (а не по тегу) в Loki работает через полный перебор строк (grep), что при объемах в 1.2 млн строк в сутки работает слишком медленно по сравнению с Elasticsearch.

### Вариант 3: Облачный стек GCP Operations Suite (Cloud Logging / Cloud Monitoring)
* *Почему отклонен:* Привязывает архитектуру TradeWare к вендору (Vendor Lock-in) и сервисам Google Cloud. Бизнес-цель компании требует подготовить решение, готовое к гибкой микросервисной миграции. Стек ELK + Prometheus является платформонезависимым и развернется в любом Kubernetes-кластере (включая локальный MiniKube или альтернативные российские облака).

## 6. Последствия решения (Плюсы и Минусы)

### Плюсы:
* **Максимальная глубина анализа:** Elasticsearch и Kibana обеспечивают лучшую скорость расследования инцидентов со сложными Java-ошибками.
* **Проактивность:** Внедрение Grafana Alerting позволяет узнавать о деградации SLA до того, как клиенты начнут жаловаться в поддержку.
* **Нулевой оверхед на бизнес-БД:** Логи и графики обрабатываются на выделенных серверах мониторинга, разгружая PostgreSQL для ERP-интерфейсов.

### Минусы:
* **Ресурсоёмкость:** Elasticsearch и Logstash требуют значительного объема оперативной памяти (JVM-хосты) для индексации и работы, что увеличивает затраты на облачную инфраструктуру GCP.
* **Сложность поддержки:** Команде DevOps необходимо администрировать и масштабировать два независимых кластера хранения данных (Prometheus для метрик и Elasticsearch для логов).
