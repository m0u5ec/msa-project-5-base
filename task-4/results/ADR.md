# ADR: Внедрение Spring Batch для асинхронных ETL-операций TradeWare

## 1. Статус
Рассмотрение к реализации пилотного прототипа / POC

## 2. Контекст и проблематика
Текущая монолитная система TradeWare на базе WildFly обрабатывает входящие CSV-отчеты объемом 400 000+ строк в сутки синхронно и построчно (Row-by-Row). В пиковые периоды строительного сезона нагрузка возрастает в 2–3 раза.

Это приводит к следующим критическим проблемам:
* Монолитная база данных PostgreSQL перегружается из-за количества транзакций, возникают взаимные блокировки.
* Пользовательский ERP-интерфейс «виснет», так как поток обработки блокирует HTTP-соединение. Происходят обрывы по таймауту.
* Отсутствует отказоустойчивость: при ошибке в середине файла весь процесс приходится начинать заново.

### Бизнес-цели и SLA к новой системе:
1. **Масштабируемость:** Надежная работа при 100–150 параллельных загрузках отчетов в пиковые часы.
2. **Производительность:** Обработка файла на 2 000 строк должна занимать **до 30 секунд**.
3. **Поэтапная миграция:** Постепенный вынос функционала из монолита без полной остановки системы и переписывания кодовой базы с нуля.

## 3. Критерии выбора решения
* **Совместимость со стеком:** Нативная интеграция с Java 11 (текущий язык бэкенда TradeWare).
* **Асинхронность:** Полное разделение фазы приема файла и фазы его обработки.
* **Эффективность работы с БД:** Поддержка пакетной загрузки данных для снижения нагрузки на PostgreSQL.
* **Надежность:** Наличие встроенных механизмов повторных попыток (Retry) и пропуска битых строк (Skip).
* **Наблюдаемость** Подробная фиксация хода выполнения каждой обработки позволяет прикрутить подробное логирование.

## 4. Предложенное решение: Внедрение Spring Batch
Принято решение вынести логику обработки отчетов из монолита WildFly в отдельный асинхронный ETL-микросервис на базе фреймворка **Spring Batch**.

### Как Spring Batch решает задачи бизнеса:
1. **Чанковая обработка (Chunk-oriented processing):** Фреймворк читает, валидирует и обогащает данные не построчно, а настраиваемыми пачками (например, по 500–1000 строк). Запись в результирующую таблицу PostgreSQL происходит одной транзакцией на чанк. Это снижает количество обращений к БД в тысячи раз и гарантирует выполнение SLA (2 000 строк менее чем за 30 секунд).
2. **Асинхронная модель:** Монолит WildFly больше не будет обрабатывать файлы. Он лишь сохраняет файл в Google Cloud Storage (GCS), отправляет легкое событие в очередь задач (GCP Pub/Sub или RabbitMQ) и мгновенно возвращает ответ сотруднику склада. Пользователю больше не нужно ждать завершения обработки.
3. **Встроенный контроль состояний (State Management):** Spring Batch автоматически сохраняет прогресс обработки в свои служебные таблицы метаданных. Если в процессе обработки 1 млн строк упадет сеть или сервер, пайплайн не нужно запускать заново — он продолжит работу ровно с того чанка, на котором споткнулся.
4. **Retry и Skip политики:** Из коробки поддерживается декларативная настройка: при временной сетевой ошибке с GCP сервис сделает 3 автоматических ретрая, а при ошибке формата конкретной строки — пропустит её и запишет в лог ошибок, не останавливая весь пайплайн.
5. **Системные таблицы Spring Batch** Фреймворк из коробки фиксирует все этапы, результаты, ошибки и количество успешно обработанных записей/чанков в своих служебных таблицах. На базе этих данных получаем возможность анализировать процессы обработки,- вся информация об ошибках, битых записях, применении ретраев и пр. фиксируется в процессе самой обработки.

## 5. Альтернативные варианты, которые рассматривались

* **Apache Airflow:**
    * *Почему отклонен:* Требует развертывания сложной обособленной Python-инфраструктуры. Для Java-команды TradeWare это увеличивает порог входа, TTM (Time to Market) и усложняет перенос существующих DTO и правил валидации.
* **Apache Spark:**
    * *Почему отклонен:* Предназначен для Big Data (терабайты данных). Для объемов TradeWare (до 1.2 млн строк в сутки) Spark избыточен. Накладные расходы памяти и времени на запуск распределенной сессии кластера превысят само время обработки файлов.

## 6. Последствия решения (Плюсы и Минусы)

### Плюсы:
* **Высокая скорость:** Пакетные транзакции убирают узкое место на стороне PostgreSQL.
* **Переиспользование кода:** Разработчики могут использовать уже написанную на Java 11 логику валидации и маппинга из монолита.
* **Идеально для миграции (Strangler Fig Pattern):** Позволяет изолированно вынести ETL-слой, не ломая Angular-фронтенд и логику интерфейсов.
* **Логирование на минималках** В минимально необходимом виде логирование ETL-процесса получаем сразу при внедрении Spring Batch.

### Минусы:
* В PostgreSQL необходимо развернуть стандартные служебные таблицы метаданных Spring Batch (`BATCH_JOB_INSTANCE`, `BATCH_STEP_EXECUTION` и др.).
* Архитектура усложняется из-за добавления промежуточного брокера сообщений для связи монолита и Spring Batch сервиса (можно в принципе обойти простой табличной очередью и статусной моделью).


## Как работает обновленное решение To Be

1. Асинхронный прием: Сотрудник склада загружает CSV-файл. Монолит на WildFly сохраняет его в GCS, кидает легкое сообщение в очередь задач и сразу же отпускает пользователя с ответом: «Файл принят, идет обработка».
2. Защита от пиков: Если 150 пользователей одновременно загрузят файлы, очередь сообщений (Pub/Sub) сдержит этот удар, не давая системе упасть.
3. Пакетный процессинг: Автономный Spring Batch ETL Сервис забирает задачи из очереди по одной (или параллельно, регулируя пул воркеров). Он открывает файл из GCS, читает его порциями (чанками) по 1000 (на уровне конфигурирования можно оптимизировать размер) строк, сопоставляет со справочниками товаров в PostgreSQL и сохраняет изменения в БД одной транзакцией на чанк.
4. Информирование: Как только Spring Batch завершает работу, он сообщает монолиту, а тот через WebSockets мгновенно перекрашивает статус обработки в браузере у пользователя в «Успешно».
